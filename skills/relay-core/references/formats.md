# Issue と PR の書式

## 方針

- **短く，上から読んで判断できる順に書く．** 読み手が最初の 3 行で「何のために，何ができれば終わりか」を分かるようにする．
- **振る舞いは例の表で書く．** 状況，入力，期待する結果を 1 行ずつ並べる．文章で条件を説明するより，境界と例外が見やすい．
- **Issue は約束，PR は記録．** Issue には予定を，PR には実際にやったことと確かめた結果を書く．
- **分からないことは分からないと書く．** 推測で path や command を埋めず，「要調査」として残す．

## 大きさ

| 大きさ | 目安                                                      | 扱い                          |
| ------ | --------------------------------------------------------- | ----------------------------- |
| S      | 1 つの関心事．差分がおおむね 200 行以下                   | そのまま実装する              |
| M      | 複数の file にまたがるが，1 回のレビューで読める          | そのまま実装する              |
| L      | 1 回のレビューで読めない，または独立した規則が複数ある    | 実装しない．epic にして分ける |

## 着手の条件

relay-build は，次を全て満たす Issue にだけ着手する．

- 「完了の姿」がある．
- 大きさが S または M である．epic ではない．
- open の依存（blocked by）がない．ただし `relay.yml` の `stack: true` で，依存先に open PR がある場合を除く．
- 他の Assignee，他の人の作業 branch，open PR がない．

## Issue の種類

| 種類 | template     | 使う場面                                         |
| ---- | ------------ | ------------------------------------------------ |
| 作業 | `task.yml`   | 機能追加，改善，文書，設定                       |
| 不具合 | `bug.yml`  | 期待と違う動作の修正                             |
| 調査 | `spike.yml`  | 決めるための調査．成果はコードではなく判断       |
| 大項目 | `epic.yml` | 複数の Issue に分けて進める目標                  |

### 作業

```markdown
### なぜ
招待の期限が切れると，管理者は member を削除して招待し直すしかない．手間がかかり，招待の履歴も消える．

### 完了の姿
- [ ] 管理者は期限切れの招待を再送できる
- [ ] 再送すると，新しい期限の招待が届き，古い招待は使えなくなる
- [ ] 管理者でない member は再送できない

### 振る舞いの例
| 状況 | 入力・操作 | 期待する結果 |
| --- | --- | --- |
| 管理者，招待は期限切れ | 再送する | 新しい招待を 1 件作り，古い招待を無効にする |
| 管理者，招待は有効 | 再送する | 再送せず，「まだ有効です」と返す |
| 管理者でない member | 再送する | 権限エラーを返す |

### 範囲の外
- 招待の期限の長さを変えること

### 手がかり
- `src/invitations/**`
- 要調査：メール送信を queue に入れているか

### 確かめ方
- 自動：再送の規則を integration test で確かめる（上の表の 3 行）
- 手動：なし
```

「振る舞いの例」は，振る舞いが変わらない作業（文書，設定，refactor）では「なし（振る舞いは変えない）」と書く．
refactor では，変えないことを確かめる方法を「確かめ方」に書く．

### 不具合

`なぜ` の代わりに次を書き，残りは作業と同じにする．

```markdown
### 起きていること
20 MB を超える file を upload すると，error にならず途中で切れた file が保存される．

### 再現手順
1. 21 MB の file を用意する
2. 添付として upload する
3. 保存された file の size を見る

### 環境
commit `abc1234`，Chrome 140，本番環境
```

「振る舞いの例」には修正後の期待を書く．「確かめ方」には，不具合を再現する回帰テストを必ず書く．
深刻度は template の選択肢（P0〜P3）で選ぶ．

### 調査

```markdown
### 問い
PDF の生成を server で行うか，browser で行うか．

### 決め方
- 日本語の font が崩れないこと
- 100 page で 10 秒以内に生成できること

### 時間の上限
1 日

### 成果物
- 比較表と結論を，この Issue の comment に書く
- 結論が今後の設計に効く場合は ADR を書く
```

時間の上限に達したら，途中の結果と，続けるかどうかの提案を comment に書いて止める．

### 大項目（epic）

```markdown
### ゴール
管理者が招待を最後まで管理できる．

### 完了の姿
- [ ] 全ての sub-issue が close されている
- [ ] 管理者が，招待する，再送する，取り消す，の一連の操作を行える

### 分け方
計画時点の案．実際の親子関係と依存は GitHub の sub-issue と blocked by で管理する．
1. 招待に期限を持たせる（S）
2. 招待を再送する（M，1 に依存）
3. 招待を取り消す（S，1 に依存）

### 範囲の外
- 一括招待
```

### title

- 作業，不具合，調査：「何を，どうする」を動詞で終える．例：`期限切れの招待を再送できるようにする`．
- 大項目：到達する状態を書く．例：`管理者が招待を最後まで管理できる`．

## PR

```markdown
Closes #12

## 変わること
管理者が期限切れの招待を再送できるようになる．古い招待は再送した時点で使えなくなる．

## 見てほしいところ
1. `src/invitations/resend.ts`：古い招待の無効化と新しい招待の作成を 1 つの transaction にした
2. `src/invitations/resend.test.ts`：Issue の例の表の 3 行を 1 test ずつ確かめている
- 判断：有効な招待の再送は error ではなく 200 と「まだ有効です」を返した．UI で error 表示にしないため

## Issue からの変更
なし

## 確かめたこと
確認した head: `a1b2c3d`

| | 確認 | 結果 |
| --- | --- | --- |
| ✅ | `npm test`（追加：`resend.test.ts` 3 件） | 128 件成功 |
| ✅ | 検出力：無効化の処理を外すと `resend.test.ts` が失敗する | 1 件失敗を確認し，戻した |
| ✅ | CI | 全 job 成功 |
| ⏭ | 手動の画面確認 | UI の変更がないため |

## 戻し方
この PR を revert する．data の migration はない．
```

### 規則

- `Closes #<番号>` を 1 行目に書き，対応する Issue を **1 件だけ** 閉じる．epic は閉じない．
- 「見てほしいところ」には，読む順序と，反対されそうな判断を書く．差分の要約を並べるだけにしない．
- 「Issue からの変更」には，Issue の予定から変えたことと理由を書く．レビューの指摘で変えたこともここに書く．
- 「確かめたこと」：
  - `確認した head:` には，表の結果を得た commit の短い SHA を書く．push したら表と一緒に更新する．
  - 状態は ✅ 成功，❌ 失敗，⏭ 未実施の 3 つだけにする．⏭ には必ず理由を書く．
  - 追加，変更したテストは，その test file と件数を確認の行に書く．
  - 不具合の修正と重要な規則では，**検出力** を確かめる．修正を一時的に外して test が失敗することを確認し，元に戻す．
- 「戻し方」には，revert だけで戻せない場合（migration，外部の設定，data の変換）の手順を書く．
- title は `relay.yml` の `pr_title` に従う．

release PR（`relay.yml` の `release`）は，この書式の例外として，含まれる PR の一覧と移行手順を書き，
`relay:release` label を付ける．Issue は閉じない．

## CI による検査

`relay-adopt` が入れる `relay-pr-policy` workflow が，PR 本文を機械的に検査する．

| 検査                                           | Draft の間 | Draft 解除後 |
| ---------------------------------------------- | ---------- | ------------ |
| `Closes` などで閉じる Issue が 1 件だけか      | 失敗       | 失敗         |
| `確認した head:` が今の head と一致するか      | 警告       | 失敗         |
| 「確かめたこと」に ❌ が残っていないか         | 警告       | 失敗         |

`relay:release` label の PR は検査しない．
