# Issue と Pull Request の執筆契約

## 目的

Issue を**実装前の作業契約**，PR を**実装後の差分と検証結果の契約**として分ける．
人間と agent のどちらが書いても，読み手が上から数十秒で「何をするか」「どこを見ればよいか」を
判断できる本文にする．

## 基本原則

1. **1 Issue = 1 PR = 1 レビュー単位**．サイズ `L` の Issue は実装せず，epic と sub-issue に分割する．
2. **予定と結果を混ぜない**．Issue は「これからどう振る舞うべきか」，PR は「実際に何を提供し，何を確認したか」を書く．
3. **振る舞いは Given-When-Then で書く**．1 規則につき 1 シナリオ，各行は 1 文にする．
4. **GitHub metadata を本文へ複製しない**．親子関係，依存，担当，label，milestone は GitHub の機能で管理する．
5. **推測で埋めない**．未確定の path や command は `未確定` と書き，決めるために必要な調査を書く．

## 要求振る舞いの書き方

```text
Scenario: 管理者が新しい member を招待する
Given: organization の管理者として認証されている
When: 新しい member を招待する
Then: organization に未完了の招待が 1 件作成される
```

- `When` は利用者が達成したい目的を書く．「button を click する」のような UI 操作を主語にしない．
- `Then` は利用者または公開境界から観測できる結果を書く．内部の関数呼び出しは書かない．
- spike では，確定済みの前提を `Given`，調査の trigger を `When`，残す判断または証拠を `Then` に書く．

## Issue

### 種類とテンプレート

| 種類                 | テンプレート                      | 自動で付く label |
| -------------------- | --------------------------------- | ---------------- |
| 作業（機能，改善，文書，調査） | `.github/ISSUE_TEMPLATE/work.yml` | なし（種別 label を手動または skill で付ける） |
| 不具合               | `.github/ISSUE_TEMPLATE/bug.yml`  | `type:bug`       |
| 大項目（epic）       | `.github/ISSUE_TEMPLATE/epic.yml` | `epic`           |

### 作業 Issue の section

| section          | 内容                                                                      | 必須 |
| ---------------- | ------------------------------------------------------------------------- | ---- |
| ゴール           | 完了したら何ができるようになるかを 1〜2 文で書く                           | ○    |
| 背景             | なぜ今必要か，現在の問題                                                  | ○    |
| 要求振る舞い     | Given-When-Then のシナリオ                                                | ○    |
| 受け入れ条件     | 第三者が完了を判定できる checklist                                        | ○    |
| テスト計画       | 振る舞いごとのテスト層と代表 case（表）                                   | ○    |
| 範囲             | 対象と対象外を並べて書く                                                  | ○    |
| 変更予定         | 変更予定の path（glob 可）．未確定なら調査内容                            | ○    |
| 確認手順         | 実装後に実行する予定の command と手動確認                                 | ○    |
| 参照             | 正本の docs，ADR，外部仕様                                                |      |
| リスクと切り戻し | 失敗したときの影響と戻し方                                                |      |

### サイズ

サイズは label（`size:S`，`size:M`，`size:L`）で表し，本文には書かない．

| label    | 目安                                                      | 扱い                     |
| -------- | --------------------------------------------------------- | ------------------------ |
| `size:S` | 1 つの関心事，差分がおおむね 200 行以下                   | そのまま実装する         |
| `size:M` | 複数ファイルにまたがるが，1 回のレビューで読める          | そのまま実装する         |
| `size:L` | レビューが 1 回で終わらない，または独立した規則が複数ある | 実装せず sub-issue に分割 |

### 着手できる状態（Definition of Ready）

agent が `implement-issue` を始めてよいのは，次を全て満たす Issue だけである．

- 要求振る舞いと受け入れ条件が書かれている．
- `size:L` ではない．
- GitHub 上の依存（blocked by）が全て close 済みである．
- 別の担当者，linked branch，open PR がない．

満たさない場合，agent は実装を始めず，不足している項目を利用者へ報告する．

### 不具合 Issue

作業 Issue の section に，`実際の動作`，`再現手順`，`環境`，`証拠`，`深刻度` を加える．
修正後の期待は `要求振る舞い` に書き，`実際の動作` と混ぜない．

| 深刻度 | 目安                                                   |
| ------ | ------------------------------------------------------ |
| P0     | data の破壊，security 事故，全利用者が使えない         |
| P1     | 主要機能が使えない，回避策がない                       |
| P2     | 機能の一部が使えない，回避策がある                     |
| P3     | 表示の崩れなど軽微なもの                               |

### epic

epic は「完了の定義」と「分解案」だけを持ち，個別のシナリオは sub-issue に書く．
分解案の表は計画時点の記録であり，実際の親子関係と依存は GitHub の sub-issue と blocked by を正本とする．

## Pull Request

### 構成

PR 本文は，読み手が上から順に判断できる順序にする．

| section              | 内容                                                                           |
| -------------------- | ------------------------------------------------------------------------------ |
| 概要                 | 何が変わるかを 1〜3 行で書き，`Closes #<番号>` を 1 件だけ書く                 |
| 概要表               | 種別，影響の大きさ，破壊的変更の有無                                           |
| レビューの入口       | 読む順序と，特に見てほしい箇所．迷う判断をした箇所はここに書く                 |
| 変更内容             | 変更を関心事ごとに箇条書きにする                                               |
| Issue との差異       | 予定から追加，削除，変更した判断と理由．なければ `なし`                        |
| 提供する振る舞い     | 実装後の Given-When-Then．Issue と同じなら `Issue と同じ` と書いてよい          |
| テスト               | 追加，変更，削除したテストと所有する振る舞い                                   |
| 確認結果             | 状態付きの表．✅ 成功，❌ 失敗，⏭ 未実施（理由を書く）                        |
| 受け入れ条件         | Issue の受け入れ条件を転記し，現在の差分で満たしたものに check を付ける        |
| 切り戻しと残るリスク | `<details>` に折りたたむ．戻し方，互換性，監視方法                             |

### 確認結果の規則

- 書けるのは，**現在の head で実際に実行した**結果だけである．
- 実行していない確認は，⏭ と理由を書いて同じ表に残す．表から消さない．
- 失敗した確認は ❌ で残し，原因と対応を書く．
- push 後に head が変わった場合は，表を新しい head の結果で更新する．

```markdown
| 状態 | 確認                      | 結果・理由                      |
| ---- | ------------------------- | ------------------------------- |
| ✅   | `bash scripts/check.sh`   | 全て成功                        |
| ✅   | CI（head `a1b2c3d`）      | 全 job 成功                     |
| ⏭   | 手動の画面確認            | UI の変更がないため不要         |
```

### Issue を閉じる記法

対応する Issue を次のいずれかで**正確に 1 件だけ**閉じる．単なる参照は `#123` と書く．
CI の `pr-policy` job がこの規則を検査する．

```text
Closes #123
Fixes #123
Resolves #123
```

### PR title

Conventional Commits の形式にする．例：`feat(auth): 招待の再送を追加する`．

## review の観点

- Issue は予定，PR は実装後の振る舞いと結果を書いている．
- 要求振る舞いが Given-When-Then で，1 シナリオ 1 規則になっている．
- 受け入れ条件と確認結果が重複していない．
- 確認結果が現在の head で実際に得た証拠だけを示している．
- GitHub metadata を本文へ複製していない．
- PR が対応する Issue を正確に 1 件だけ閉じている．
